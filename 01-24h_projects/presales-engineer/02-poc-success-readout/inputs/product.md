# Fictional Lantern product and engagement facts

These facts are authoritative for this exercise. Do not add capabilities, dates or commitments that are not listed here.

- **P1 — Mobile analysis:** Lantern runs static and dynamic analysis of customer-authorized Android (APK/AAB) and iOS (IPA) builds. iOS dynamic analysis requires a development- or ad-hoc-signed IPA. An App Store-encrypted IPA receives **static analysis only**. Lantern also detects third-party dependencies in mobile builds.
- **P2 — Web analysis:** Lantern runs authenticated dynamic testing (DAST) of customer-authorized web apps and REST APIs. Authentication uses a recorded login sequence or a static bearer-token header. A login protected by MFA needs a test account with MFA disabled, or a token. A scan profile can include or exclude paths. Lantern has **no GraphQL-specific testing**: a GraphQL endpoint is scanned only as a generic HTTP endpoint. There is no source-code analysis of web repositories.
- **P3 — Findings and identity:** Severity is `critical`, `high`, `medium`, `low` or `info`; it is a prioritization label, not proof of exploitability. Status is `open` (not yet triaged), `confirmed` (customer analyst verified the issue; not yet fixed), `false_positive` (customer analyst rejected it), `risk_accepted` (customer accepted the risk) or `fixed`. A JSON export lists **one row per detection**, so one finding can appear in several rows. `fingerprint` is the stable identity of a finding across rows, scans and exports; `finding_id` is only a row number inside one export.
- **P4 — Rescans:** When a rescan covers a finding's location and no longer detects it, Lantern sets the status to `fixed`. A finding whose location is outside the rescan scope is **not included** in the rescan export; it keeps its last reported status and has not been retested.
- **P5 — CLI:** `lantern scan mobile --file <path> --plan <name> --wait --fail-on <severity>`. Exit code 0 = scan completed, no open finding at or above the threshold; 1 = scan completed, at least one open finding at or above the threshold; 2 = scan error or timeout; 3 = authentication or configuration error, such as a bad API key or missing file. The API key is read from the `LANTERN_API_KEY` environment variable.
- **P6 — Jira Cloud:** Lantern creates Jira issues from findings and syncs status in both directions. Lantern → Jira updates follow Lantern status changes. Jira → Lantern updates apply **only to Jira statuses mapped** in the Lantern project settings; a change to an unmapped Jira status is ignored by design. Mappings can be edited by a project admin at any time.
- **P7 — Assurance limits:** Scan results do not guarantee that an app is secure and are not a compliance certification. Lantern does not issue statements of security to regulators. A SOC 2 Type II report about Lantern's own service is available under NDA.
- **P8 — PoC terms and roles:** A PoC lasts 14 days. An extension of up to 7 days requires approval from the account executive, Noor. The sales engineer owns the technical readout and technical next steps. Sales engineers cannot authorize extensions, discounts, roadmap dates or contract terms. ServiceNow integration and GraphQL-specific testing are listed as "exploring"; they have no committed date.
